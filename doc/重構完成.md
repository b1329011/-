# 不揪ㄛ - 後端與資料庫重構完成說明文件

本文件詳細紀錄了針對後端（Django）與資料庫（MySQL）所進行的整合重構、欄位對齊以及球類與程度中文化修改。

---

## 一、 資料庫 (MySQL Schema / SQL) 修改

1. **`users` 資料表**：
   - 新增 `email` 欄位：`email varchar(255) NOT NULL UNIQUE` (用作主揪與成員登入的唯一認證帳號)。
2. **`gamesmatches` 資料表**：
   - 廢除舊有 `is_free` 欄位，球局費用改為由 `total_price` (十進位) 欄位統一管理。
   - 新增 `duration` 欄位：`duration varchar(50) NOT NULL DEFAULT '2 小時'`，用以儲存球局預計進行時長。
   - 將原有的 `description` 欄位更名為 `game_note` (`game_note text`)，用於球友發起球局時備註佔位或服裝要求。
   - 程度欄位 `target_level` 之 ENUM 值修改為中文選項：`enum('C(初學者)','B(熟練)','A(高手)','S(菁英)')`。
3. **`user_sport_levels` 資料表**：
   - 解除 user_id 為主鍵的 UNIQUE 限制（原結構會造成同一用戶無法在多個運動有不同等級），新增了單一主鍵 `id` 欄位：`id int(11) NOT NULL AUTO_INCREMENT`。
   - 等級欄位 `level` 之 ENUM 值修改為中文選項：`enum('C(初學者)','B(熟練)','A(高手)','S(菁英)')`。
   - **django不支援復合主鍵**
4. **`keep` (收藏球局) 資料表**：
   - 為了支援多對多關係並相容 Django Admin 等後台工具，新增了 `id` 自增主鍵：`id int(11) NOT NULL AUTO_INCREMENT`。原複合主鍵 `(user_id, game_id)` 改為 `UNIQUE KEY`。
5. **`sports` 資料表種子資料**：
   - 將預設球類中文化以保持高度一致：`'Basketball'` -> `'籃球'`, `'Badminton'` -> `'羽毛球'`, `'Volleyball'` -> `'排球'`, `'Mahjohn'` -> `'麻將'`。

---

## 二、 後端 (Django Backend) 修改

### 1. 模型層 (`api_v1/models.py`)

- **中文化 Choice 定義**：在 `UserSportLevel` 和 `GameMatch` 中，全面改用中文程度選項作為 Choice 限制。
- **認證系統對齊**：保留自訂 user manager 邏輯與 AbstractBaseUser 認證欄位（自動同步至本地測試 SQLite 資料庫中）。
- **關係欄位對齊**：將經緯度儲存位置由 `Address` Model 完全移至 `Venue` Model。

### 2. 序列化驗證層 (`api_v1/serializers.py`)

- **球局發起時間與截止日自動計算**：
  - 前端發起球局時不再需要手動傳送 `time_slot`，改為傳送 `start_time` (如 `"18:00"`) 與 `duration` (如 `"2 小時"`)。
  - 後端在 `validate` 階段會自動解析並組裝出 `time_slot` (如 `"18:00-20:00"`)；若無提供取消截止時間，會自動將 `cancel_deadline` 設定為活動開始前 24 小時（或活動前 1 小時）。
- **運動程度輸入防呆**：
  - 前端發起球局或註冊完善檔案時，不論傳入的是單一字母 (`'C'`, `'B'`, `'A'`, `'S'`)、英文舊格式 (`'B(advanced)'`) 還是中文 (`'B(熟練)'`)，後端都會在序列化驗證時將其自動映射標準化為中文名稱存入資料庫，兼顧前端便利性與資料庫一致性。
- **強固的防呆校驗限制**：
  - **價格限制**：`total_price` 必須在 `0 ~ 10,000` 元之間。
  - **人數限制**：最多人數 `most_players` 必須大於 0，且不能少於最少人數 `least_players`。
  - **時間格式限制**：持續時間必須包含有效數字，且時長必須在 `0.5 ~ 24` 小時之間。
  - **預約過去日期限制**：球局的預約日期 `booking_date` 不能早於今天。

### 3. 業務邏輯視圖層 (`api_v1/views.py`)

- **球局預約必有場地限制**：發起球局時，後端會強制檢查並解析出對應運動的球場 `Court`。若解析無效（即該場館沒有能打該球類的球場，或無對應場地），會立刻回傳 `400` 錯誤，防範空場地建立。
- **運動程度比對相容性邏輯**：在隊員加入球局 `join_match` 的等級審核階段，映射表 `level_map` 同時支援了中文、英文以及單字母等級的比對（例如：擁有 `'B(熟練)'` 證書的玩家可以加入要求 `'casual'` 或 `'B'` 或 `'B(熟練)'` 的球局）。
- **GPS 距離過濾**：Haversine 距離計算與 OpenData 同步邏輯中的經緯度來源已對齊到 `Venue`。

## 三、 自動測試程式

- 建立了第一階段自動測試腳本
- 自動執行並驗證了 A 帳號的正常使用邏輯，以及 B 帳號的不正常錯誤格式輸入（日期為過去、超出價格限制、持續時間非法、人數上限矛盾、性別限制無效、手機號碼錯誤、未完善檔案即加入球局等防呆），所有測項均 100% 成功攔截並回傳 400 錯誤。
